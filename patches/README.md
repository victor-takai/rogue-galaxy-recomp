# Patches to pinned dependencies

`ps2recomp/` holds changes to the framework in `thirdparty/PS2Recomp`. The
submodule stays at its upstream commit; `cmake/framework_patches.cmake`
applies each patch here to its checkout, in name order, when the game is
configured and before `python setup.py tools` builds the recompiler (some
patches change the code it generates), and skips one that is already
applied (listed in `thirdparty/PS2Recomp/.rg-patches-applied`, or
`git apply --reverse --check` for one not listed yet). To undo them, run
`git -C thirdparty/PS2Recomp checkout -- .` and delete that stamp.

To change the newest patch, edit the checkout and regenerate it from a
base that holds the earlier ones: a detached `git worktree` of the
submodule at its commit with patches 0001 to N-1 applied and committed,
the modified files copied over it, `git diff` into the patch file. Then
check that the new patch reverse-applies to the checkout. A later patch
may change lines an earlier one added (0011 does, in 0004's and 0006's;
0012 in 0010's), after which the earlier one no longer reverse-applies
(today 0004, 0006, 0008 and 0010 do not); the stamp file is
what keeps configure from applying it again (before the stamp this
failed twice, 2026-10-19). A build does not reconfigure by itself, so
run `cmake -S . -B build/game` once after.

| Patch | Why |
|---|---|
| `0001-dma-start-observer.patch` | `PS2Memory::setDmaStartObserver`: a callback before any DMA transfer runs. The VIF1 thread (`src/vif1_thread.cpp`) uses it to order transfers the game starts through the registers behind the VIF1 lists it is still running. |
| `0002-gs-release-prepared-frames.patch` | The GS worker drops its reference to each prepared presentation as soon as it is ready. It kept them until the end of its batch, and each holds one of the SDL backend's three presentation slots: a batch with four presentations, which flip pacing queues when the worker falls behind on light frames (a loading screen), waited on itself forever. |
| `0003-ee-guest-rounding.patch` | Guest code runs with the EE's floating point mode: results rounded toward zero, denormals as zero (PCSX2's default, MXCSR 0xFFC0). Under round-to-nearest, code that rounds with the 1.5 * 2^23 trick gets the next integer: Rogue Galaxy's angle wrap adds a full turn to small angles, and characters in battle swing back and forth around their target every frame. `PS2X_EE_ROUNDING=nearest` keeps the host's mode. |
| `0004-mxcsr-rounding-reads.patch` | The GS worker queue read the rounding mode with `std::fegetround` for every command (one per primitive from the VIF1 thread), and the VU1 core switched it with `fesetround` for every MSCAL; MinGW's go through the CRT and touch the x87 control word too, 7% of the VIF1 thread. Both read and set MXCSR directly on x86. |
| `0005-vif1-bulk-xgkick-plain-unpack.patch` | Two cuts to the VIF1 thread. An XGKICK's packet went out a quadword per two simulated cycles even after the program had ended or while it stalled on its next XGKICK, where nothing can write VU memory any more: those two cases now copy the rest at once, at the clock the copy would have reached (`VU1Interpreter::gatherXgkick`, `flushPipelines`, `Run::stall`). And UNPACK's common shapes (no mask, no row add, CL >= WL, 32/16/8-bit) go straight into VU memory instead of through the generic loop that reads the destination back, decodes through lambdas and masks every lane (`unpackPlain`). |
| `0006-vu1-fmac-flags-ee-timer-batch.patch` | Three cuts on the emulation threads. The VU1 flags: `compile_vu_programs.py` decides pair by pair whether a MAC flag reader (FMEQ, FMAND, FMOR) can still see an FMAC's result (`flag_liveness`: a later FMAC that lands before any reader kills it; a call, a register jump or a pair left to the interpreter keeps it; the E bit ends it), and the compiled pair queues the result only then (`Block::flags`, `Frame::issue<..., Needed>`). The status flags are sticky, so an image that reads them (FSEQ, FSAND, FSOR; `VU1Interpreter::fmacFlagsWanted`, from a bit per pair that `PS2Memory::markVU1CodeWritten` keeps as the VIF's MPG writes the code, so no scan of the image after each of the game's code uploads, which was 2% of the VIF1 thread; a write from the EE side rescans once) queues every result, as does `PS2X_VU_FMAC_FLAGS=1`. Rogue Galaxy reads status flags nowhere, and 138 of its 1775 FMAC pairs keep their flags; the map's routine went from 14% to 9% of the VIF1 thread and `commitFlags` from 7% to 3%, byte-identical frames at 1x and 3x. And `PS2Memory::advanceEeTimers`, called at every guest safe point, batches its cycles to 2048 before walking the timers (a compare or overflow interrupt arrives up to 7 us late); the timer register reads and writes settle the batch first, so they see the exact count. And a texture split over DIRECT packets (a GIF IMAGE continuing in the next DIRECT) is handed to the GS in place through `PS2Memory::setGifImageCallback` / `GS::processImageContinuation` instead of being copied whole behind a synthesized IMAGE tag, which was 5% of the VIF1 thread in the streets. |
| `0007-vu-region-counters-extern.patch` | `ps2_vu_detail::regionCounters`, a thread_local with a destructor, is declared `extern` in `ps2_vu1_region.h` and defined once in `ps2_vu1_core.cpp`: as an inline variable every translation unit including the header emitted its TLS initialization wrapper, and lld on COFF refuses the duplicates as soon as the compiled VU blocks' shards (`PS2X_VU_AOT_IMAGES`, 32 of them) include it. Needed to compile the game's VU0 micro programs as blocks. |
| `0008-dispatch-single-lookup.patch` | `PS2Runtime::dispatchGuestBranch` looks the target up in the function table once, for the presence test and the call, instead of `hasFunction` and then `lookupFunction` (which looked again). It runs for every inter-function transfer of the generated code; with File 03's three characters the dispatcher was 7% of the game thread and the second lookup 3%. The dispatch history still records the call. |
| `0009-ee-thread-end-report.patch` | The scheduler says on stderr when a guest thread ends with pc 0 outside any callback (a jump to address 0, or a return past the entry) and when the main thread calls ExitThread or ExitDeleteThread, with the registers and the last 64 dispatched pcs (`PS2Runtime::dispatchHistory`, new). Before, the thread went dormant silently, and a game whose main thread did so looked frozen with every other thread waiting on a semaphore (Rogue Galaxy, 2026-10-19: a hit that poisoned and knocked the player down). |
| `0010-dispatch-unwind-not-a-return.patch` | The freezes' cause. `PS2Runtime::dispatchGuestBranch` forgives a callee that comes back with pc still at its entry (a host stub that never set pc) by continuing at the fallthrough. A scheduler checkpoint unwinds the guest the same way, pc at the entry of the function the innermost frame was about to call; when that is also an outer in-flight frame's callee (indirect recursion: the config script VM while loading, the action dispatch on a knockdown, the script runner on a skill) the outer frame took the unwind for a return and resumed its caller with the inner frame's registers and stack pointer, and the next epilogue read a stale slot: the main thread ended at pc 0, or jumped into its own stack. The dispatcher now forgives only with the stack pointer back where the call left it: the unwind comes from a deeper frame, a stub never leaves sp moved. Found by the 2026-10-19 review from the two memory dumps. A first version used a scheduler flag set by the checkpoint and cleared on guest entry; it went stale when the scheduler resumed another thread suspended inside a stub (that resume is not a new entry), the stub's return was taken for an unwind and the stub ran twice, which made the scripted walk diverge from run to run and once hung a load. |
| `0011-review-fixes.patch` | Smaller findings of the same review. An FMAC-class upper with an empty dest mask publishes no flags (`upperPublishesFlags`, and `compile_vu_programs.py`'s liveness agreed only by luck: none of the recorded routines crosses a zero word). The EE timer batch delivers a late interrupt even when no timer is cued any more, and the idle wait settles the batch before computing its deadline. A thread that ends because its pc names no function says so (the report behind it prints once per process). A VU0 micro program that runs out of its 4096-cycle budget is reported (`VU1Interpreter::lastRunEnded`). |
| `0012-dispatch-unwind-per-thread.patch` | The stack-pointer rule of 0010 missed one case: a frameless leaf whose loop head is its own entry (`StrCmpU8`, 0x1834B0, comparing names for `DirTableFindFile`) unwinds from its back edge with pc at the entry and sp unmoved, and the lookup went on with a character for the comparison's result. The scheduler now counts the guest unwinds a checkpoint starts (`noteGuestUnwind`, from `eeCheckpointDue` and the dispatcher's own safe point) and records on each guest thread the serial of its latest; the dispatcher forgives a callee left at its entry only when sp is back and that thread started no unwind during the call. The count is per thread, so another thread's unwinds while a stub waited (what made the flag of 0010's first version stale) do not count. Found by the 2026-10-20 review. |
| `0013-gs-finish-queued.patch` | `GSThreadedBackend::Sync(Finish)` is queued for the worker instead of draining the queue: the backend's part of a FINISH (the queued draws go to the GPU) keeps its place in order, and the CSR bit is the front end's. The drain held the GS front end (the VIF1 thread, then the GIF stage) at every FINISH until the worker had caught up. Syncs that read something back (LocalToHost, DebugReadback, Reset, Presentation) still wait. |
| `0014-vu1-whole-register-writes.patch` | Compiled VU1 programs write a VF register or ACC as one 16-byte store, blending the written lanes into the old value (`Frame::writeVector`), instead of one store per lane. A masked write (xyz: an 8-byte and a 4-byte store) cannot forward to the next pair's 16-byte read of the register, which then waits for both stores to retire; that wait was the hottest instruction of Rogue Galaxy's busiest routine. About 2% of the VIF1 thread at a boss gate; frames byte-identical. |
| `0015-gs-queue-geometric-growth.patch` | The GS worker's queue grows geometrically. Publishing a stage of commands behind pending ones reserved exactly the new size, so the queue grew one stage at a time and, while the worker was behind, every publish of 128 commands moved the whole queue (up to its 16 MB) into a new block. At a scene's first frames, with the worker building textures and waiting on readbacks, that made the GIF stage the bottleneck and held the presenter on the submission lock: the frame after Rogue Galaxy's boss-gate load took 0.6 s. The append is a range insert, so a failed allocation throws before any command moves. |
| `0016-dispatch-jump-unwind.patch` | A jump the dispatcher hands back to the scheduler (an unresolved `jr`, or a direct jump to an address with no function) unwinds the host frames as a checkpoint does, and now counts as one for the forgiveness of 0010 and 0012 (`noteGuestUnwind`): a frameless function jumping back to its own entry through a register, sp unmoved, would have been taken for a stub's return by an outer call. Not seen in Rogue Galaxy; found by the 2026-10-20 afternoon review. |
| `0019-gs-source-tag.patch` | `ps2_gs_detail::t_sourceTag`, a thread_local the submitting thread sets (the game's VIF1 thread names the VU1 program it is running, `src/vif1_thread.cpp`); `GSThreadedBackend::Submit` stamps it on each `GSPrimitiveBatch` (`sourceTag`, 0 for none). Profiling only: the GS backend's per-program counts and the census read it. |
| `0020-gs-source-camera.patch` | `ps2_gs_detail::SceneCamera` (the viewport, projection and view matrices a VU1 program ran under, read from VU1 data memory) and `CameraRegistry`, which keeps the newest 4096 and hands out ids (the same camera as the last keeps its id). The submitting thread names one in `t_sourceCamera`; `GSThreadedBackend::Submit` stamps its id on each batch (`GSPrimitiveBatch::sourceCamera`) and the renderer looks it up, for the jitter and motion vectors of the 3D scene. |
| `0021-gs-native-mesh.patch` | `GSNativeMesh`: a strip a VU1 program would have drawn, as the program's inputs (object-space positions, UVs, colors, its matrix, fog and culling), for the game's `src/vu1_native.h`. `GS::submitNativeMesh` hands it to the backend under the draw state of the moment, in order with the packets; `GSThreadedBackend` queues it for the worker. `GSRasterBackend::SubmitNativeMesh` expands it by default into the triangles the program would have kicked (`gsExpandNativeMesh`, with the per-vertex arithmetic `gsNativeMeshPoint` that the game's packet path uses too); the SDL GPU backend transforms it on the GPU. `GS::currentDrawState` is `buildDrawBatch`'s state, factored out. |

A new patch is the output of `git -C thirdparty/PS2Recomp diff` for the
files it changes, with the earlier patches applied.
